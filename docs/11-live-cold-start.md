# Чистая установка: от пустого диска до проверенного клиента

Маршрут конкретного выпуска: V4.1 EXL3 + 2×H200 + CUDA 13 toolkit + Linux x86_64. Все адреса берутся из **новой** аренды. Ни сохранённых весов, ни старого venv, ни JIT cache не предполагается. Для другого checkpoint использовать [общий runbook](08-portable-deployment.md).

## 0. Подготовить проект на ноутбуке

Получить архив комплекта или clone опубликованного репозитория после его публикации. Сейчас публичный URL не создан, фиктивная команда clone здесь не приводится. На GPU-машину копируется **код**, не готовые веса.

До оплаты проверить предложение: две нужные GPU и NVLink, CPU/RAM, большой локальный диск с запасом, доступный toolkit/nvcc, сеть. Исходный стенд имел 855 GiB диска и около 967 GiB RAM cgroup; это измеренный пример, не минимальные требования.

## 1. Новый сервер и инвентаризация

Войти по команде SSH из панели, прочитать руководство провайдера, сверить host key. Скопировать комплект в каталог, например `/workspace/webinar`. Далее серверные команды выполняются из корня комплекта:

```bash
mkdir -p .local
bash ops/inspect.sh /workspace > .local/inventory.txt
cat .local/inventory.txt
cp profiles/exl3-h200.env.example .local/server.env
```

Отредактировать `.local/server.env`: `ROOT` на большом диске, например `/workspace/model-run`; реальные `CUDA_HOME`, `UV_BIN`, `TP`, arch. Пути MODEL_PATH/ENGRAM_PATH/PYTHON_BIN выводятся из ROOT. Начальный контекст 65536 нужен для дальнейшего free-code; первый запуск на первоначальном стенде начинался с 8192.

Проверить фактическую GPU-архитектуру: `9.0a` — H200 baseline. Показать, что каталоги MODEL_PATH/ENGRAM_PATH ещё отсутствуют или пусты. Не удалять имеющиеся данные для создания видимости «с нуля»: арендовать пустой каталог/узел.

Проверить отсутствие чужой нагрузки и порт 18080. Если шаблон стартовал Qwen, определить его службу и только на своей аренде остановить согласованный шаблонный inference. Не трогать caddy/portal/tunnel_manager. Внимание: `ops/inspect.sh` печатает возможные диагностические ошибки и не заменяет оценку inventory человеком.

## 2. Предварительная проверка и независимый downloader

```bash
bash ops/exl3.sh .local/server.env preflight &&
bash ops/exl3.sh .local/server.env deps
```

Preflight проверяет Linux x86_64, необходимые команды, toolkit 13.0, две свободные H200, порт и оставшийся объём весов + 100 GiB запаса на том же диске. Это консервативная проверка конкретного H200-профиля; она намеренно не одобряет другие GPU. RAM/cgroup, NVLink и тип диска пока проверяются человеком по inventory. 100 GiB — эксплуатационный запас, а не измеренный минимум. Для 4×H100 80GB этот preflight не запускать: готовый маршрут в [рецепте H100](12-h100-4x80.md). Для прочей машины сначала адаптировать профиль по общему runbook.

Требуется установленный `uv` (путь можно задать через UV_BIN), Python 3.12, `git`, `g++`, toolkit с `nvcc`. Если базовый образ отличается и этого нет, исправить состав окружения до следующего этапа; не менять host driver внутри контейнера. Этот рецепт не устанавливает host driver.

## 3. Два независимых терминала

**Терминал A — веса:**

```bash
set -o pipefail
bash ops/exl3.sh .local/server.env download 2>&1 | tee .local/download.log &&
bash ops/exl3.sh .local/server.env verify 2>&1 | tee .local/verify.log
```

**Терминал B — runtime:**

```bash
set -o pipefail
bash ops/exl3.sh .local/server.env install 2>&1 | tee .local/install.log &&
bash ops/exl3.sh .local/server.env kernels 2>&1 | tee .local/kernels.log
```

Downloader использует свой небольшой venv, поэтому не ждёт сборки ExLlama. Installer защищён каталогом `.install-lock` от одновременной записи в один runtime. Не запускать два downloader в один каталог весов. Оба терминала должны завершиться успешно. Если install упал, не выдавать продолжающуюся загрузку за успешно готовящийся runtime: открыть первую ошибку и [каталог диагностики](09-lessons-and-errors.md).

Стадии не пропускаются автоматически по существованию marker-файла. Повтор download использует pinned snapshot и HF metadata; `verify` читает полный SHA256. Возобновление установки после сбоя требует чтения ошибки — это не гарантированная транзакция с любым промежуточным состоянием venv.

## 4. Запуск и прогрев

После успешных install + kernels + verify:

```bash
bash ops/run-model.sh .local/server.env --dry-run
set -o pipefail
bash ops/exl3.sh .local/server.env serve 2>&1 | tee .local/server.log
```

Команда работает в foreground, `Ctrl-C` остановит модель. Во втором терминале после `Application startup complete`:

```bash
bash ops/exl3.sh .local/server.env smoke
```

Ожидаются три PASS: completed generation, SSE, real file tool round trip. `/health` и список моделей без этих запросов недостаточны. Для постоянного сервиса после демонстрации подходит [Supervisor-шаблон](../profiles/supervisor.conf.example); не требуется менять manager ради одного эфира.

### 4a. Быстрый режим

Baseline-профиль работает в eager и без спекуляции: на 4×H100 это 11 токенов/с в один поток против 58 с быстрыми настройками. После трёх PASS остановить сервер (`Ctrl-C`), в `.local/server.env` раскомментировать блок fast path (`EAGER=0`, CUDA graphs, DSpark), запустить снова и повторить smoke. Затем замер:

```bash
python3 ops/bench-decode.py --model deepseek-v4.1-flash --parallel 1,1,4
```

В логе до готовности должны быть `[dsv41-exl3-pretune]` и `Graph capturing finished`. Если захват графов падает, вернуть `EAGER=1` — это baseline, уже прошедший smoke. На H200 быстрый режим ещё не проверялся: включать его на репетиции, по одному шагу за перезапуск. Флаги, выбор схемы под другое число GPU и ловушки — в [docs/13](13-speed.md).

## 5. UI и подключение с ноутбука

Если в образе есть штатный Model UI:

```bash
python3 ops/configure-model-ui.py --api-base http://127.0.0.1:18080 \
  --model deepseek-v4.1-flash --max-output 4096
# После проверки preview:
python3 ops/configure-model-ui.py --api-base http://127.0.0.1:18080 \
  --model deepseek-v4.1-flash --max-output 4096 --apply
supervisorctl restart model-ui
```

В панели открыть Launch Application / Secure Tunnel Link. Токенизированную ссылку не публиковать в чате вебинара. В отсутствие этого UI использовать API/клиент: он не является требованием самого inference.

На ноутбуке задать **новые** SSH_TARGET/SSH_PORT/LOCAL_PORT/REMOTE_PORT и запустить `ops/tunnel.sh`. Для free-code создать профиль по [инструкции клиента](10-clients-and-operations.md), затем выполнить Read и [учебную задачу](../examples/demo-project/README.md). Старый туннель/адрес не использовать по памяти.

## 6. Завершение

Сохранить обезличенные результаты и профиль без ключей на ноутбук. Завершение аренды/диска выполняется владельцем через панель после проверки, что нужный код и отчёты сохранены. Постоянное хранение весов не требуется: manifest обеспечивает повторное получение тех же файлов, но следующая загрузка снова займёт время.

Этот сценарий локально проверяется как код и порядок стадий. **Полная холодная GPU-репетиция ещё не выполнена.** До неё нельзя обещать запуск одной командой за фиксированное число минут.

## Если этап завершился ошибкой

| Этап | Что делать дальше |
|---|---|
| preflight | Исправить конкретную причину в inventory/профиле, затем повторить preflight. Скрипт не освобождает GPU и не меняет драйвер автоматически |
| deps | Проверить uv, Python 3.12 и доступ к индексам; повторить deps. Downloader изолирован от runtime |
| download | Проверить сеть и свободный диск, повторить ту же команду с тем же manifest. HF использует сохранённые части; не менять revision ради продолжения |
| verify | При отсутствующем файле повторить download. При неверном SHA переместить только повреждённый shard вне MODEL_PATH/ENGRAM_PATH, проверить бюджет диска, повторить download и полный verify. Простого повторного download может быть недостаточно: HF доверяет локальной metadata |
| install | Читать первую ошибку в install.log. Не обновлять всё до latest. После обычного выхода lock снимается; после SIGKILL сначала проверить отсутствие installer и лишь затем удалить пустой ROOT/.install-lock командой rmdir. При неизвестном состоянии venv взять новый ROOT и повторить установку; старые данные автоматически не удалять |
| serve | Проверить оба успешных отчёта SHA, install.log, версии, пути и первую ошибку server.log; найти симптом в каталоге ошибок. Не запускать второй экземпляр на те же GPU |
| smoke | Сохранить ошибку и server.log. Запуск не принят, даже если health отвечает. Отдельно проверить generation/SSE/tool cycle |

После успешного install сохраняется `ROOT/reports/pip-freeze.txt`; constraints закрепляют известные основные версии, но **полного проверенного dependency lock пока нет**. Не терять freeze при завершении аренды. Изменение версий требует повторной приёмки.

## Приёмка повторяемости

- [ ] Новый пустой ROOT; зафиксированы образ, driver/toolkit, GPU, RAM/cgroup и диск.
- [ ] Preflight, deps, install, download и оба SHA256 завершились без ошибок.
- [ ] Installer проверил зависимости и небольшую CUDA-операцию на обеих GPU.
- [ ] Стадия kernels прошла EXL3 GEMM/MoE и Engram dequant на каждой GPU; Torch matmul сам по себе их не заменяет.
- [ ] Завершённая генерация, SSE и tool/file round trip прошли.
- [ ] Model UI (если используется) и реальный клиент проверены.
- [ ] После перезапуска снова прошёл smoke.
- [ ] Все необходимые исправления внесены в скрипты; второй человек может пройти только по документу.
- [ ] Профиль без секретов, freeze и обезличенные результаты сохранены вне сервера.

Галочки ставятся по результату новой чистой установки. Исторически работающий стенд не закрывает этот список автоматически.
