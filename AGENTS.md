# Работа с комплектом развёртывания

Это переносимые материалы для запуска моделей на арендованном GPU-сервере.
Текущая проверенная модель — DeepSeek V4.1 Flash; следующий узел, формат весов,
движок и провайдер могут отличаться. Не считать EXL3, H200, Vast или конкретный
SSH-адрес обязательными условиями проекта.

## Начало работы

1. Для EXL3 с пустого диска начать с `docs/11-live-cold-start.md`. Прочитать `README.md`, `docs/08-portable-deployment.md` и выбранный профиль.
2. Разделять **измерено на стенде**, **проверено локально**, **предположение для
   нового узла**. Даты, commits, model revision и доказательства сохранять.
3. Уточнить фактический формат через config/quantization metadata, индекс весов
   и model card. Название репозитория не доказывает формат. FP8 не равен BF16.
4. На новом сервере прочитать местные AGENTS/CLAUDE и руководство провайдера.
   На Vast: `/etc/vast-agents-guide.md`. Выполнить `ops/inspect.sh`.
5. Определить физические GPU, доступную VRAM, topology, cgroup RAM/CPU,
   архитектуру CPU, host driver, toolkit/nvcc, свободный диск, mount persistence,
   текущие GPU-процессы и занятые порты. Root внутри контейнера не равен host root.
6. Выбрать совместимый checkpoint/runtime/GPU, закрепить ревизии. Не ставить
   `latest`, чтобы молча обойти несовместимость. Не использовать Docker-in-Docker
   или смену драйвера в контейнере как стандартный способ ремонта.

## Где искать

- `skills/<имя>/SKILL.md` — готовые рецепты с конфигом и скриптами, для любого агента и человека.
  Сначала проверить, нет ли скила под задачу. FP8 на vLLM и **любые замеры скорости** —
  только по `skills/ds4-fp8-vllm/SKILL.md`: `serve.sh` + `bench.sh`, иначе числа несравнимы.
  Сборка, подключение и проверка клиента free-code (команда `free-code`, флаг `--yolo`) —
  по `skills/free-code-deepseek/SKILL.md`. Исходники free-code: https://gitverse.ru/krestnikov/free_code
- `docs/08-portable-deployment.md` — общий runbook и развилки EXL3/FP8/BF16.
- `docs/09-lessons-and-errors.md` — причины, симптомы, исправления и границы переноса.
- `docs/10-clients-and-operations.md` — API, Model UI, free-code, управление.
- `docs/07-vast-exl3.md` — датированный опыт конкретного работающего стенда.
- `ops/` и `profiles/` — переносимые инструменты и начальные профили.
- `deploy/` — специфичные patches EXL3 и сохранённые команды стенда; читать перед запуском.
- `scripts/` и `docs/03-runbook.md` — прежний FP8 Docker-рецепт, не универсальный installer.
- `model-manifest.json`, `quantized-manifest.json` — pins и SHA256 от HF;
  `deploy/weights-verified.json` — фактический SHA256-аудит 41 EXL3/Engram файла.

## Изменения и приёмка

- По умолчанию занимать **все доступные GPU узла** ради максимальной скорости; ограничивать
  карты только по прямой просьбе владельца. Не выводить «4 GPU» из того, на чём снят эталон.
- Адреса, пути, TP/EP, контекст, concurrency, CUDA arch и имена моделей — параметры.
  GPU-архитектуру не выводить из рекламного имени арендного шаблона.
- Не переносить EXL3 patches на FP8/BF16. Специфичный patch должен проверять
  версию/ожидаемый фрагмент и останавливаться при расхождении исходников.
- Не удалять чужие процессы/веса/кэши. Замена занятой модели — только в порученном
  контуре с разрешением, учитывая уже данное разрешение. Не требовать Qwen rollback:
  владелец текущего стенда явно отказался от него. Для нового узла контекст иной.
- API по умолчанию loopback и SSH, либо штатный gateway с авторизацией. Не отключать
  Vast Caddy auth ради удобства. Не останавливать portal/caddy/tunnel_manager.
- Секреты не включать в профили, команды, отчёты и git. Использовать env/key store,
  файл 600. Не выгружать целиком environment, /proc/environ, конфиги auth и историю.
- Сначала импорт/маленькая CUDA-операция и проверка loader, затем веса с SHA256,
  запуск с одним запросом, законченная генерация, SSE, tool round trip,
  фактический клиент, перезапуск. Health/RUNNING недостаточно.
- Учитывать JIT: первый запрос может быть медленным. Оптимизацию графов, fat kernels,
  batch, DSpark и длинного контекста делать отдельно после корректного baseline.
- Любое заявление о скорости сопровождать workload, числом токенов, warm/cold,
  версиями и настройками. Выделение KV cache не доказывает рабочий полный контекст.
- Проверки переносимых утилит: `python3 -m unittest discover -s tests -v`,
  `bash -n ops/*.sh` по одному файлу; dry-run обоих профилей. GPU-проверку обозначать
  отдельно: локальные unit tests не подтверждают работу новой GPU/модели.
- Изменение документации не означает поручение менять работающий сервер.
  Перед редактированием читать файл. Репозиторий публичный:
  https://github.com/Rai220/ds4f_nolimit_webinar. Commit и push — только по просьбе владельца.
  В git не класть имена узлов, SSH-адреса и логины аренды, IP, токены.
